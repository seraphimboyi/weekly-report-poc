# 工作日誌與週報產生工具 POC 規格書

Nov 4, 2026 · @Boyi　（2026/11/05 依實作更新為「每日記事」版本；2026/11/10 補上週次規則、常用項目、回顧頁）

## 背景與目標

這個 POC 讓同仁平日用幾秒記錄工作，週五一鍵產出符合現行範本的 Word 週報。

現況是每個人的記錄方式不同、資料散落各處，每週還要手動整理一份 Word 週報，內容分成「本週工作項目」與「下週預計工作項目」兩張表。

**POC 目標**

- 平日記錄一筆工作約 10 秒內完成
- 週報「本週工作項目」自動帶入並隨記事更新，使用者只需檢視、補上進度與預計完成日、微調
- 匯出的 .docx 與現行範本格式一致，不需要額外調整
- 資料結構預留欄位，未來可以擴充為團隊共享

## 使用者與使用情境

POC 先做個人使用，團隊共享留到第三階段。

| 階段 | 使用者 | 資料可見範圍 |
| --- | --- | --- |
| POC（MVP） | 開發者本人與少數試用同仁，各自使用 | 只有自己 |
| 第三階段 | 團隊成員 | 團隊共享，細節待定 |

主要情境有兩個：平日做完一件事後隨手記一筆；週五整理週報時，打開工具檢視、補上進度與預計完成日、微調後匯出 Word。

## MVP 範圍

MVP 只做「記錄 → 週報 → 匯出」這條主線，其他功能一律往後放。

**要做**

- 本週記事：「一週」是週三到下週二，畫面五格（週三、四、五、一、二），直接在每一格新增記事，可切換週次補記
- 記事的新增、編輯、刪除（刪除前二次確認）
- 常用項目：維護常用的工作項目清單，新增記事時快速填入
- 回顧頁：聊天室式 AI 問答，用一般說法查過去的記事（透過 LiteLLM，API key 只放在後端）
- 週報頁：自動帶入本週表，可以編輯、刪除、新增列，修改自動保存
- 週報自動跟著最新記事更新，且不覆蓋使用者改過的欄位
- 進度、預計完成日、下週工作項目都在週報頁由使用者管理
- 匯出套用現行範本的 .docx
- 以 Docker 部署到內部主機

**先不做**

- 登入與帳號管理（先寫死單一使用者）
- 團隊共享、主管彙整
- AI 潤飾文字（回顧頁的 AI 問答不屬於此項，週報內容仍不使用 LLM）
- 標籤分類、進階搜尋
- 任務完成／暫停狀態
- 文件整理類功能

## 使用流程

**平日（每天重複）**

1. 打開首頁「本週記事」，點今天那一格的「＋ 新增記事」展開表單
2. 填「工作項目」（必填）；需要的話填「備註」（選填）
3. 按 Enter 儲存；Shift+Enter 可在欄位內換行

補記其他天：切到該週，點那一格的「＋ 新增記事」。週六、日不開放新增。

**週五（整理週報）**

1. 打開「週報」頁，系統已依本週記事帶入「本週工作項目」
2. 在本週表填「目前進度」與「預計完成日」
3. 要列入下週的項目，按該列的「→ 加入下週」（手機是卡片上方的文字按鈕），再到下週表填預計達成進度與備註
4. 視需要編輯、刪除或新增任何一列
5. 按「匯出 Word」下載 .docx

**回顧（隨時）**

打開「回顧」頁，用一般說法問過去的記事（例如「我上個月做了什麼？」、「幫我整理今年的績效自評素材」）。伺服器先由 LLM 解析問題的期間與工作項目，再撈對應的記事回答；對話記錄只存在瀏覽器的 sessionStorage，關閉分頁就會清掉。回顧只讀記事，不讀週報的進度與預計完成日。

## 記事

| 欄位 | 必填 | 說明 |
| --- | --- | --- |
| 日期 | 是 | 記事所在的那一天，由所在的格子決定 |
| 工作項目 | 是 | 使用者自己填；同名的記事在週報合併成一列；可換行 |
| 備註 | 否 | 做了什麼；可換行 |

- 工作項目與備註是同樣的輸入框：會隨內容長高，Enter 儲存、Shift+Enter 換行
- 工作項目沒有預設值，系統不會從上次的記事帶入；工作項目欄下方有「最近使用」（最近 6 種）與「常用項目」兩個按鈕，點選清單項目才會填入；常用項目在 `/favorites` 頁面新增、改名、刪除、調整順序，不影響已寫的記事
- 週六、日不開放新增記事；資料庫裡若已有週末記事（舊資料），首頁才會多顯示一列唯讀的「週末」；週報不帶入週末的記事

## 週報自動帶入規則

週報由程式依固定規則產生，**不使用 LLM**。最後內容由使用者在預覽頁決定；預覽頁的修改只存在這份週報裡，不回寫到記事。

| 欄位 | 一、本週工作項目 | 二、下週預計工作項目 |
| --- | --- | --- |
| 帶入哪些 | 本週（週三到下週二，不含週六、日）有記事的工作項目，同名的合併成一列 | 不自動帶入；使用者在本週表按該列的「→ 加入下週」才加入 |
| 不帶入 | 週末的記事；本週沒有記事的項目 | — |
| 工作項目描述 | 工作項目名稱 | 加入時帶入本週表的名稱 |
| 進度 (%) | 一律留白，由使用者在週報頁填 | 預計達成進度，留白由使用者填 |
| 預計完成日 | 一律留白，由使用者在週報頁用日期選擇器填 | 加入時帶入本週表的預計完成日，可再修改 |
| 備註 | 該項目本週所有記事的備註，每筆一行、由舊到新；跨多天時每天第一筆前面先加一行 `MM/DD`（日期自成一行、同一天只出現一次），單一天不加；沒填備註的記事不產生空行 | 留白由使用者填 |
| 排序 | 不自動排序，新列放最後；表格標題旁有「依預計完成日排序」按鈕，由使用者手動按（由近到遠，沒填的排最後） | 同左 |

**其他規則**

- 進度與預計完成日都由使用者手動填寫，系統不自動計算，也不從記事帶入
- 兩張表都不會自動排序，同步與編輯日期都保留現有順序；使用者按「依預計完成日排序」才會重排，日期相同或沒填的維持原順序，排完立即保存
- 使用者在預覽頁可以刪除、修改、新增任何一列
- 週報草稿自動保存，匯出後記錄為「已匯出」，保留歷史紀錄

**自動更新**

使用者不需要手動「產生」或「重新產生」：

- 打開當週週報頁（或切回分頁、匯出時），系統自動建立或同步週報
- 沒被使用者改過的名稱與備註跟著最新記事更新；改過的欄位、填寫的進度與預計完成日不會被覆蓋
- 新的工作項目會自動加一列；項目本週已沒有記事且該列沒被改過就移除；使用者自己新增的列永遠保留
- 使用者刪掉的本週列不會被加回來，表格下方有「已移除 N 項」可以加回
- 下週表完全由使用者管理，同步不會增減或修改它
- 只有「當週」自動套用；過去週次不自動改動，有更新時頁面頂端顯示「套用更新」橫幅由使用者決定；未來週次不產生
- 已匯出的週報之後只要有更新或修改，狀態就回到草稿
- 「從頭重新產生」收在選單裡，會清除所有手動修改（含下週表），需確認

## 資料模型

資料以「每日記事」為主，因為週報要的是「這週做了哪些工作項目、各自做了什麼」，使用者不需要先建立任務。

| 資料表 | 用途 | 主要欄位 |
| --- | --- | --- |
| entries | 每日記事 | id、user_id、visibility、date、project（工作項目，必填）、content（備註，選填）、created_at、updated_at |
| weekly_reports | 週報內容 | id、user_id、week_start、week_end、content（兩張表的 JSON，含手動修改紀錄）、status（draft／exported）、exported_at；一週一份 |
| favorite_projects | 常用項目 | id、user_id、name、sort_order；`(user_id, name)` 唯一。只是新增記事時的填入捷徑，與 entries 沒有關聯，改名、刪除都不影響既有記事與週報 |
| tasks、logs | 舊版任務與日誌 | 已轉成 entries；資料表保留作備份，程式不再使用 |

- `user_id` 與 `visibility` 先寫死單一使用者、預設 private，第三階段接登入與共享時不需要改表結構
- `entries` 另有 `progress`、`due_date`、`carry_over` 三個欄位已不使用（進度、預計完成日、下週項目都改在週報頁管理），先保留不刪
- 沒有 `weekly_plans` 表：下週表的內容直接存在週報 JSON 裡
- `weekly_reports.content` 是預覽頁的內容，也是匯出 Word 時套版的資料來源

## 技術架構

MVP 只有一個 Next.js 專案：前端頁面透過 API Route 讀寫 SQLite，匯出時由後端用 docxtemplater 套範本產生 .docx，單一容器部署。回顧頁透過後端呼叫內部的 LiteLLM（OpenAI 相容），API key 只放在後端、不傳到瀏覽器。

| 項目 | 選擇 | 理由 |
| --- | --- | --- |
| 框架 | Next.js（App Router） | 開發者熟悉，前後端放同一個專案 |
| 資料庫 | SQLite，搭配 Drizzle ORM | 單一檔案、免架設；之後可移到 Postgres |
| 輸入驗證 | zod | API 輸入一律驗證 |
| Word 匯出 | docxtemplater | 直接套現行範本，樣式完整保留 |
| AI 問答 | LiteLLM（OpenAI 相容 API），伺服器端用原生 `fetch` 呼叫 | 只用於回顧頁；沒設定時其他功能不受影響 |
| 部署 | Docker，放到內部主機 | 沿用既有的部署方式；容器啟動時自動套用 migration |

## Word 範本套版

直接拿現行的週報 Word 當範本，用 docxtemplater 填入資料，字型、框線、欄寬等樣式全部保留。

**現行範本結構**

| 區塊 | 內容 |
| --- | --- |
| 頂端 | 工作區間：2026/xx/xx-2026/xx/xx |
| 一、本週工作項目 | 序號、工作項目描述、目前進度 (%)、預計完成日期、備註；預留 4 列 |
| 二、下週預計工作項目 | 序號、工作項目描述、預計達成進度 (%)、預計完成日、備註；預留 4 列 |

**改造內容（已完成）**

1. 「工作區間」改成 `{weekStart}-{weekEnd}`
2. 兩張表都只留標題列與一列資料列，資料列改成迴圈標記：本週表 `{#thisWeek}…{/thisWeek}`、下週表 `{#nextWeek}…{/nextWeek}`，項目有幾筆就產生幾列
3. 移除灰底範例列與空白列；表頭底色、字型、框線、欄寬保留原樣
4. 資料列統一使用淡藍底色，不再一列淡藍、一列白色交錯（已確認可接受）
5. 範本放在專案內的 `templates/weekly-report.docx`，公司範本改版時重新放標記並替換這個檔案

**週報內容 JSON 格式**

這份 JSON 就是 `weekly_reports.content` 存的內容，也是匯出時套進範本的資料。序號、百分比與日期格式都由程式先整理好，範本不做任何計算；沒填的欄位留白；名稱與備註可含換行，會轉成 Word 的換行。

```json
{
  "weekStart": "2026/11/04",
  "weekEnd": "2026/11/10",
  "thisWeek": [
    { "no": 1, "title": "…", "progress": "60%", "dueDate": "2026/11/13", "note": "…" }
  ],
  "nextWeek": [
    { "no": 1, "title": "…", "targetProgress": "100%", "dueDate": "2026/11/13", "note": "" }
  ]
}
```

| 欄位 | 說明 | 範例 |
| --- | --- | --- |
| weekStart、weekEnd | 工作區間，週三到下週二，格式 YYYY/MM/DD | 2026/11/04 |
| thisWeek | 本週工作項目，保留現有順序（使用者可手動依預計完成日排序） | — |
| nextWeek | 下週預計工作項目，保留現有順序（使用者可手動排序） | — |
| no | 序號，由程式依順序產生 | 1 |
| title | 工作項目描述 | DocExtractor_FE 上傳頁面調整 |
| progress | 目前進度（只在 thisWeek），含 % 的字串，由使用者填 | 60% |
| targetProgress | 預計達成進度（只在 nextWeek），含 % 的字串，由使用者填 | 100% |
| dueDate | 預計完成日，格式 YYYY/MM/DD，由使用者填 | 2026/11/13 |
| note | 備註，可留白；換行會轉成 Word 的換行 | 11/03 完成拖曳上傳 |

實際儲存的 JSON 還有同步與編輯用的欄位（每列的 `id`、`groupKey`、`touched`，以及整份的 `dismissed`），範本不使用、會忽略；細節見 `CLAUDE.md`。

## 待決事項與風險

- [x] 已決定：「一週」是週三到下週二（連續 7 天），週報只撈週三、四、五、一、二這五天的記事；週六、日不開放新增記事。設定集中在 `lib/config.ts`，之後要改只需調整一處。週末的工作由使用者在預覽頁自行補上。
- [x] 已決定：進度、預計完成日、下週工作項目都只在週報頁由使用者管理。
- [ ] 團隊共享的可見範圍，留到第三階段再定

**風險**

- 採用率：同仁若不習慣平日記錄，週報就帶不出東西。對策是把記錄做到極輕，並允許週五直接在預覽頁補寫
- 範本改版：公司若更改週報格式，需要重新放套版標記
- SQLite 只適合單機小量使用，團隊共享前應先移到 Postgres
- 沒有登入機制：部署到內部主機時應限制在內網存取
