# 工作日誌與週報產生工具 POC 規格書

Nov 4, 2026 · @Boyi

## 背景與目標

這個 POC 讓同仁平日用幾秒記錄工作，週五一鍵產出符合現行範本的 Word 週報。

現況是每個人的記錄方式不同、資料散落各處，每週還要手動整理一份 Word 週報，內容分成「本週工作項目」與「下週預計工作項目」兩張表。

**POC 目標**

- 平日記錄一筆工作約 10 秒內完成
- 週報兩張表自動帶入，使用者只需檢視與微調
- 匯出的 .docx 與現行範本格式一致，不需要額外調整
- 資料結構預留欄位，未來可以擴充為團隊共享

## 使用者與使用情境

POC 先做個人使用，團隊共享留到第三階段。

| 階段 | 使用者 | 資料可見範圍 |
| --- | --- | --- |
| POC（MVP） | 開發者本人與少數試用同仁，各自使用 | 只有自己 |
| 第三階段 | 團隊成員 | 團隊共享，細節待定 |

主要情境有兩個：平日做完一件事後隨手記一筆；週五整理週報時，打開工具檢視、微調後匯出 Word。

## MVP 範圍

MVP 只做「記錄 → 週報 → 匯出」這條主線，其他功能一律往後放。

**要做**

- 工作項目（任務）的新增、編輯、標記完成或暫停
- 在任務底下寫每日日誌，順手更新進度
- 進度用滑桿加 +10%、+20% 快捷按鈕手動填寫，記住上次的數值
- 週報預覽頁：自動帶入兩張表，可以編輯、刪除、新增列，草稿自動保存
- 匯出套用現行範本的 .docx
- 以 Docker 部署到內部主機

**先不做**

- 登入與帳號管理（先寫死單一使用者）
- 團隊共享、主管彙整
- AI 潤飾文字
- 專案標籤、進階搜尋
- 文件整理類功能

## 使用流程

&#91;embedded content: 使用流程 · 平日 3 步、週五 4 步\]

平日的記錄每天重複；週五系統把累積的任務與日誌帶入草稿，使用者在預覽頁確認無誤後，才按「匯出 Word」產生 .docx。

## 週報自動帶入規則

系統只負責帶入初稿，最後內容由使用者在預覽頁決定；預覽頁的修改只存在這份週報的快照裡，不回寫到任務資料。

| 欄位 | 一、本週工作項目 | 二、下週預計工作項目 |
| --- | --- | --- |
| 帶入哪些任務 | 所有「進行中」的任務，加上「本週內完成」的任務；本週沒有日誌的進行中任務也帶入 | 所有尚未完成的任務，預設全部勾選 |
| 不帶入 | 更早之前完成的任務；「暫停」的任務（可手動加回） | 已完成的任務 |
| 工作項目描述 | 任務名稱 | 任務名稱 |
| 進度 (%) | 目前進度；本週完成者為 100% | 預計達成進度，留白由使用者填 |
| 預計完成日 | 任務的現值 | 任務的現值 |
| 備註 | 本週最近一筆日誌，沒有就留白 | 留白由使用者填 |
| 排序 | 預計完成日期由近到遠 | 預計完成日期由近到遠 |

**其他規則**

- 進度一律手動填寫（同仁平常就是憑感覺估），系統不自動計算
- 使用者在預覽頁可以刪除、修改、新增任何一列
- 週報草稿自動保存，匯出後記錄為「已匯出」，保留歷史紀錄

## 資料模型

資料以「工作項目（任務）」為主、日誌掛在任務底下，因為週報範本是以工作項目為單位，而且要填進度和預計完成日。

| 資料表 | 用途 | 主要欄位 |
| --- | --- | --- |
| tasks | 工作項目 | id、user\_id、visibility、title（工作項目描述）、progress（目前進度 %）、due\_date（預計完成日）、status（進行中／已完成／暫停）、completed\_at |
| logs | 每日日誌 | id、task\_id、date、content（今天做了什麼）、progress\_after（記錄當下更新的進度，選填） |
| weekly\_plans | 下週計畫 | task\_id、week、target\_progress（預計達成進度 %）、note（備註） |
| weekly\_reports | 週報快照 | id、user\_id、week\_start、week\_end、content（兩張表的 JSON 快照）、status（draft／exported）、exported\_at |

- `user_id` 與 `visibility` 先寫死單一使用者、預設 private，第三階段接登入與共享時不需要改表結構
- `completed_at` 用來判斷「本週內完成」
- `weekly_reports.content` 是預覽頁的修改結果，也是匯出 Word 時套版的資料來源

## 技術架構

&#91;embedded content: 技術架構 · MVP 一個容器，LiteLLM 為第二階段\]

MVP 只有一個 Next.js 專案：前端頁面透過 API Route 讀寫 SQLite，匯出時由後端用 docxtemplater 套範本產生 .docx。虛線的 LiteLLM 是第二階段才接，API key 只放在後端。

| 項目 | 選擇 | 理由 |
| --- | --- | --- |
| 框架 | Next.js（App Router） | 開發者熟悉，前後端放同一個專案 |
| 資料庫 | SQLite，搭配 Drizzle ORM | 單一檔案、免架設；之後可移到 Postgres |
| Word 匯出 | docxtemplater | 直接套現行範本，樣式完整保留 |
| 部署 | Docker，放到內部主機 | 沿用既有的部署方式 |

## Word 範本套版

直接拿現行的週報 Word 當範本，用 docxtemplater 填入資料，字型、框線、欄寬等樣式全部保留。

**現行範本結構**

| 區塊 | 內容 |
| --- | --- |
| 頂端 | 工作區間：2026/xx/xx-2026/xx/xx |
| 一、本週工作項目 | 序號、工作項目描述、目前進度 (%)、預計完成日期、備註；預留 4 列 |
| 二、下週預計工作項目 | 序號、工作項目描述、預計達成進度 (%)、預計完成日、備註；預留 4 列 |

**改造內容（已完成）**

1. 「工作區間」改成 `{weekStart}-{weekEnd}`
2. 兩張表都只留標題列與一列資料列，資料列改成迴圈標記：本週表 `{#thisWeek}…{/thisWeek}`、下週表 `{#nextWeek}…{/nextWeek}`，項目有幾筆就產生幾列
3. 移除灰底範例列與空白列；表頭底色、字型、框線、欄寬保留原樣
4. 資料列統一使用淡藍底色，不再一列淡藍、一列白色交錯（已確認可接受）
5. 範本放在專案內的 `templates/weekly-report.docx`，公司範本改版時重新放標記並替換這個檔案

**週報快照 JSON 格式**

這份 JSON 就是 `weekly_reports.content` 存的內容，也是匯出時套進範本的資料。序號、百分比與日期格式都由程式先整理好，範本不做任何計算；沒填的欄位留白。

```json
{
  "weekStart": "2026/11/02",
  "weekEnd": "2026/11/06",
  "thisWeek": [
    { "no": 1, "title": "…", "progress": "60%", "dueDate": "2026/11/13", "note": "…" }
  ],
  "nextWeek": [
    { "no": 1, "title": "…", "targetProgress": "100%", "dueDate": "2026/11/13", "note": "" }
  ]
}
```

| 欄位 | 說明 | 範例 |
| --- | --- | --- |
| weekStart、weekEnd | 工作區間，週一到週五，格式 YYYY/MM/DD | 2026/11/02 |
| thisWeek | 本週工作項目，依預計完成日排序 | — |
| nextWeek | 下週預計工作項目，依預計完成日排序 | — |
| no | 序號，由程式依順序產生 | 1 |
| title | 工作項目描述 | DocExtractor\_FE 上傳頁面調整 |
| progress | 目前進度（只在 thisWeek），含 % 的字串 | 60% |
| targetProgress | 預計達成進度（只在 nextWeek），含 % 的字串 | 100% |
| dueDate | 預計完成日，格式 YYYY/MM/DD | 2026/11/13 |
| note | 備註，可留白；換行會轉成 Word 的換行 | 預計週三交付測試 |

## 開發里程碑

MVP 分四步，依序完成，每一步都有可以實際操作驗收的結果。

1. **任務與日誌**：任務的新增、編輯、完成、暫停；在任務下寫日誌並更新進度；資料存在 SQLite
   - 驗收：重新整理頁面後資料仍在；一筆日誌可在 10 秒內記完
2. **週報預覽頁**：依帶入規則產生兩張表，可編輯、刪除、新增列，草稿自動保存
   - 驗收：帶入結果符合規則表；關掉頁面再打開，草稿修改仍在
3. **Word 匯出**：改造範本，按下「匯出 Word」產生 .docx
   - 驗收：匯出的檔案用 Word 打開，格式與現行範本一致，列數與預覽頁相同
4. **部署**：Docker 化，放到內部主機，SQLite 檔案掛在 volume 上
   - 驗收：同仁用瀏覽器可以開啟使用；重新部署後資料不消失

## 待決事項與風險

- [ ] 已決定：「一週」固定為週一到週五，只撈這五天的資料；設定集中在程式的設定檔，之後要改只需調整一處。週末加班的工作由使用者在預覽頁自行補上。
- [ ] 已決定：本週完成的任務不出現在下週表格。
- [ ] 團隊共享的可見範圍，留到第三階段再定

**風險**

- 採用率：同仁若不習慣平日記錄，週報就帶不出東西。對策是把記錄做到極輕，並允許週五直接在預覽頁補寫
- 範本改版：公司若更改週報格式，需要重新放套版標記
- SQLite 只適合單機小量使用，團隊共享前應先移到 Postgres
